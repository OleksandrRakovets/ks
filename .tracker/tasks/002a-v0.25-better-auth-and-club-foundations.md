# T002A - v0.25 Better Auth and manager/player foundations

## Status

- [ ] Planned

## Why

The guest/session model is enough for live match sharing, but it is not enough for longer-lived ownership and management surfaces. Before adding management UI, KS needs signed-in manager auth plus the smallest supporting entities for club-scoped management and verified player records.

## Outcome

KS supports signed-in managers through Better Auth, with club membership foundations and verified player records that later management features can build on without inventing a second ownership model.

## Terminology

- Use `club` as the grouping term in product and DB planning. Do not introduce `organization` unless product scope expands beyond club-centered use.
- Use `manager account/session` for auth identity in product language.
- Use `super admin` for the elevated auth role that can perform cross-club bootstrap/admin tasks such as initial verified-player import.
- Use `verified player record` for the domain entity representing a real player.
- Do not model verified player records as manager accounts.
- Managers may create and manage verified player records, but are not linked to them as the represented player.

## Scope

- implement Better Auth in the RR7 app runtime,
- add the minimal manager account/session entities needed for signed-in management,
- add club entities and the smallest membership/role model needed to express manager-scoped responsibilities plus the super-admin role,
- add verified player records and the smallest linking rules needed for later product features,
- add a super-admin-only bulk import path to seed the initial verified player list,
- define how guest-created match/session access coexists with manager-owned resources,
- add only the smallest account/identity UI needed to sign in and confirm the model works.

## Proposed Slice Order

1. Choose and document the minimal Better Auth integration shape for the RR7 worker runtime.
2. Add auth storage and runtime wiring.
3. Add manager account, club, membership, and super-admin role foundations.
4. Add verified player record foundations and their relation to clubs where needed.
5. Add the super-admin bootstrap import flow for the initial verified player list.
6. Define and implement the boundary between guest match access from `T002` and manager-owned resources.
7. Add the smallest sign-in/account UI needed to exercise the flow.

## Acceptance

- a manager can sign in through Better Auth,
- the system can represent club-scoped manager responsibilities for later management features,
- a super admin can seed the initial verified player list through a bulk import flow,
- verified player records have a clear persistent model distinct from manager accounts,
- `T002` guest access still works and does not get replaced by a second ad hoc sharing model,
- later management tasks can reuse this identity model instead of inventing their own auth rules.

## Explicitly Deferred

- full club administration UI,
- advanced account settings,
- broad player directory UX,
- tournament management.

# T002 - v0.2 access and permissions

## Status

- [ ] Planned

## Why

The current control-secret approach is enough to move fast, but it is not the intended product model. We want one canonical match route, server-side guest identity, and explicit edit permission without introducing full manager auth too early.

## Outcome

Editability is decided server-side per match and per guest identity, and an editor can explicitly invite another device to edit the same live match.

## Scope

- assign and persist a guest identity cookie server-side,
- make the canonical match route the primary route for live control/display decisions,
- add an invite URL that authorizes another guest/device and redirects to the canonical match route,
- distinguish read-only and editable sessions on the same match,
- add the smallest management helpers needed to share and inspect access safely.

## Proposed Slice Order

1. Model guest session identity and match editor authorization in storage.
2. Add canonical match route access checks.
3. Add invite flow and redirect.
4. Remove or downgrade the old broad control-secret path.
5. Add simple UI to show whether this device can edit and how to invite another editor.

## Acceptance

- match creator can edit from the device that created the match,
- another device can gain edit access only through the invite flow,
- opening the canonical match URL on a fresh device is read-only by default,
- server-side access rules, not client guesses, decide editability.

## Notes

- This milestone should document the guest authorization concept directly in markdown as part of the task work.
- This milestone is intentionally guest/session-first; signed-in manager auth moves to `T002A`.
- Keep the implementation small and compatible with future manager-scoped ownership and club-scoped management.
- This is the access-control foundation later milestones should reuse before adding new resource-specific auth models.
